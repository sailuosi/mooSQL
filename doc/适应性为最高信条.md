# 适应性为最高信条 —— mooSQL 在夹缝中成长

> 一篇关于为什么会有 mooSQL、它长成什么样、以及在 AI 时代它还站在哪的随笔。

---

说起 mooSQL 的成长，很难用「从零设计一个理想 ORM」来概括。它更像是在夹缝里求生：平台限制、第三方实体、多种业务形态、少见数据库、复杂权限与复杂 SQL……一层层挤过来。活下来的办法只有一个——**适应性成为最高信条**。

一切能适配、能个性化的行为，尽量不写死在框架中心，而交给可替换的那一层。于是很早便定下了骨架：**Client + Dialect**（客户实例 + 方言）。方言，成了最关键的特性。

---

## 七件事：夹缝里逼出来的能力

### 1. 无法定制自己的特性 —— 先适应别人的世界

先天在一个封闭的开发平台内萌芽。挑战很直白：不可能按自己的喜好去定义实体特性。于是第一件事不是「发明一套注解」，而是**适应第三方实体特性**，再进一步**适应 Sugar 的特性**。特性解析进入方言：业务侧可以自行适配，框架只提供可插拔的解析路径。别人的规矩，变成自己能走的路。

### 2. 没有依赖，没有表对应的实体？没问题

很多 ORM 默认「有实体才有世界」。mooSQL 从一开始就允许：**没有实体也能干活**。表结构可以不映射成类，查询、写入仍可围绕 SQL 与结果集展开。依赖少、约束少，才能在受限平台和杂乱存量库里扎根。

### 3. 要简单：会 SQL 就能用？可以

不强制先学一套「框架方言」再写业务。会 SQL，就能用 SQLBuilder 把语句搭起来、执行出去。贴近 SQL 的链式方法（`select` / `from` / `where` …），降低的是心智税，不是表达力。

### 4. 多个数据库连接位，同时随意用？没问题

天生多库，不是事后补丁。连接位可以同时存在，业务里轻松**拿 A 库的数据写 B 库**。跨库搬数、对照、同步这类「平台型」需求，不必绕一大圈去造第二套上下文。

### 5. 换数据库也能行，少见库也要能适配

MySQL、SQL Server、Oracle、PostgreSQL、SQLite 之外，还有 OceanBase、Taos、GBase、Oscar 这类不那么「大众」的库。差异不堆在业务代码里，而按库定制方言——换库、加库，代价落在方言扩展上，而不是推倒重来。

### 6. API 要流畅，还要能支持实体？行，加

自由 SQL 不等于永远不要实体。需要流畅 API、需要实体映射与快捷 CRUD 时，在开放分层上往上加：仓储、实体查询、表达式路径，按需取用，而不是用实体把底层锁死。

### 7. 超复杂 SQL：CTE、子查询、权限、组装、多重 or/and？行

复杂查询 + 复杂权限，是真实业务系统里的常态，不是演示 Demo。CTE、子查询、权限片段嵌入、动态组装、多个 or/and 糅合——这些必须能在同一条构建链上表达清楚，并且最终 SQL **看得见、调得了**。黑盒翻译解决不了的，交给可拼装的 SQL 编织。

---

## 架构信条一：Client + Dialect

在这样的背景下，**客户实例 + 方言**成为最重要的架构。

- **Client**：连接、执行、多库位、事务与上下文——业务拿到的是「这一次对话」的入口。
- **Dialect**：一切可适应、可个性化的行为皆入方言。

举例：

| 要适应什么 | 交给谁 |
|------------|--------|
| 实体特性怎么解析 | 特性解析方言（业务可自行适配） |
| 分页 / 函数 / 标识符差异 | 按数据库定制的方言 |
| 少见库、特殊语法 | 新方言或方言扩展，而不是改业务层 |

框架中心尽量稳定；变化落在方言。这是「夹缝求生」留下的结构记忆。

---

## 架构信条二：分层开放

不想被一种 API 绑架，就分层开放，让场景自己选层：

| 你想要什么 | 用什么 |
|------------|--------|
| 自由 SQL、高性能、SQL 可见可控 | **SQLBuilder** |
| 实体字段选择 + 语法提示，又不喜欢纯 LINQ | **SQLClip**（SQLBuilder + 实体字段选择器） |
| 数据库管理、建表与结构能力 | **DDLBuilder** |
| 标准化、简洁的常规增删改查 | **仓储（Repository）** |
| 对标主流的表达式查询 | **Queryable**（后期建立） |

自下而上：方言与 Client 托住上下文；其上先是最高性能、最高自由度的 SQLBuilder；再上是能利用实体、有提示的 SQLClip；再后才是对标生态的 Queryable。层与层之间是开放关系，不是「只能从顶层进、底层永远封死」。

## 业务背景：它是被哪些项目养大的

多年来，主要业务背景大致是这些：

1. **复杂查询 + 复杂权限**的业务系统  
2. 追求**高度 SQL 自由、可空可拼**的流程引擎  
3. 追求**数据库管理能力**的开发平台  
4. 追加的**轻量、高性能**设备数据接收程序  
5. 以及现在的**标准化 + 简洁**的仓储查询

不同项目把不同层推到前台：有时是编织器，有时是 DDL，有时是仓储。适应性信条，正是在这些「不像同一类产品」的需求之间，仍能共用一套 Client + Dialect 而成立的。

## AI 时代：手艺还在，重心变了

ORM 的「好用」标准，其实换过好几代：

1. **API 简约流畅、好记** —— 少背文档，链式写下去；  
2. **有实体语法提示，不用复制列名** —— 减少魔法字符串；  
3. **开发人员不再关心具体编写** —— 专注业务逻辑，并让 **AI 易懂、易改、易核验**。

在我这边的项目里，现状很清楚：

- **仓储**承担了约 **90%** 的常规增删改查；  
- **SQLBuilder**承担了约 **90%** 的个性化业务逻辑 SQL；  
- 二者合起来，覆盖了大约 **80%** 的真实场景。

LINQ 的便捷性掩不住对 SQL 翻译的黑盒弊端。复杂条件、权限片段、大模型直接给出的 SQL——大家更习惯**能轻松看见 SQL 的 SQLBuilder**：既安全（参数化、进同一套方言与执行上下文），又易读（人与 AI 都能对着最终语句核对）。大模型推荐的 SQL，落到 SQLBuilder 上，往往是一条很顺的路径。

所以在 AI 驱动开发的今天，mooSQL 并没有追求「再造一个更黑的 ORM」，而是让**仓储扛标准路径，SQLBuilder 扛个性化与 AI 协作路径**——这仍然是适应性：适应当下的人，也适应当下的工具。

## 一点感叹

作为 AI 大面积介入编码之前，手头上费时三年多的最后一个「代码手艺品」，后面的新生项目，再难有仔细打磨每个类、每个方法的那种感受。

没有空前，但算是一个「绝后」了。
